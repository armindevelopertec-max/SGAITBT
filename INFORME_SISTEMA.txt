2.3 iniciar.sh (162 líneas, bash con set -euo pipefail)
--------------------------------------------------------------------------------
Flujo:
 1. Carga .env si existe (si no, usa defaults de dev).
 2. Verifica prerequisitos: docker, docker compose/docker-compose, node, npm.
 3. docker compose up -d postgres minio pgadmin redis.
 4. Espera healthchecks (60 intentos x 2s) de sga_postgres, sga_minio, sga_redis.
 5. npm install si falta node_modules (backend y frontend).
 6. npm run build (backend) y npm run seed (idempotente; si falla solo avisa).

    ./iniciar.sh --background (segundo plano).

3.1 Seguridad y jerarquía de autorización
--------------------------------------------------------------------------------
- Login: POST /api/auth/login (username o email + password mínimo 6).
  Búsqueda username → fallback email. Verifica estado ACTIVE.
- Contraseñas: bcryptjs con 10 salt rounds.
- Bloqueo: 5 intentos fallidos → status BLOCKED; login exitoso resetea contador.
- JWT: payload {sub, username, email, role, fullName, roles[], permissions[]},
  HS256, expiración 24h (JWT_EXPIRATION).
- Guías por request:
  * JwtAuthGuard: valida firmas/token y usuario ACTIVE.
  * PermissionsGuard: semántica OR sobre @RequirePermission; wildcard '*'.
  * JwtStrategy.validate recarga roles y permisos desde BD en CADA request
    → revocación de permisos inmediata.
- Auditoría: decorador @Audit + AuditInterceptor (registra solo en éxito,
  fail-safe, captura usuario, IP, entidad, valor anterior/nuevo en jsonb)
  aplicado en persons, employees, roles.

3.2 Validación global
--------------------------------------------------------------------------------
ValidationPipe estricto: whitelist, forbidNonWhitelisted, transform,
enableImplicitConversion. Los DTOs usan class-validator (IsString, IsNotEmpty,
IsDateString, @ValidateNested/@Type, IsEnum, IsObject, Min/Max, etc.).

--------------------------------------------------------------------------------
Diagrama de jerarquía:

  Institution (1) ──< Career (N) ──< AcademicPeriod (N)   [gestiones por carrera]
                          ├──< Subject (N)
                          │     └──< SubjectAssignment (N)   [paralelo+docente+aula]
                          │           ├──< SubjectEnrollment (N) >── (N) Student
                          │           ├──< Grade (N) >────────── (N) Student
                          │           └──< Attendance (N) >───── (N) Student
                          └──< Student (N) ──< Enrollment (N) ──> AcademicPeriod

  Person (1) ──< Employee (N)

7. REGLAS DE NEGOCIO CLAVE
--------------------------------------------------------------------------------
1. Códigos correlativos:
   - Estudiante : EST-{año}-{NNNN}
   - Matrícula  : MAT-{año}-{NNNNN}
   - Depósito   : DEP-{año}-{NNNN}
   - Empleado   : EMP-{NNNNN}
2. Matrícula requiere depósito habilitado: enroll-student solo acepta estudiantes
   con depósito VERIFIED o APPROVED (ranking APPROVED > VERIFIED).
3. Calificaciones:
   - 1er parcial 25% + 2do parcial 25% + prácticas 20% + examen final 30%.
   - Escala 0–100; NOTA MÍNIMA = 51 para aprobar (APPROVED/FAILED).
   - No duplica: índice único (studentId, assignmentId).
   - El estudiante debe estar inscrito en la materia (SubjectEnrollment).
   - createBulk y update recalcular y sincronizan el historial (syncHistory).
4. Sincronización historial: GradeService.syncHistory crea/actualiza
   academic_history por estudiante+materia+gestión; delete de la nota borra su
   historial.
5. Conclusión de estudios: el summary, al completar el último nivel
   (career.numberOfLevels) con 0 reprobadas y 0 pendientes →
   StudyConclusionStatus.COMPLETED y marca al estudiante como GRADUATE
   automáticamente.
6. Asistencia: registro masivo; no permite dos registros para la misma
   fecha+asignación; percentage = (present+late)/total*100; <75 → lowAttendance.
7. Asignaciones: rechaza duplicado (materia+gestión+paralelo); paralelo default
   'A'; auto-assign inscribe a todos los matriculados ACTIVE de la gestión (o a
   studentIds dados).
8. Períodos: nombre en secuencia romana (I/2026, II/2026); estados OPEN/CLOSED;
   open/close por endpoint específico.
9. Usuarios: username y email únicos; createStudentUser usa CI como username y
   password inicial; asignación de roles vía replaceRoles (reemplazo total).
10. Periodo current del estudiante: currentPeriodId (período en curso).

8. SEED Y DATOS DEMO (src/seed/seed.ts) — idempotente, npm run seed
--------------------------------------------------------------------------------
1. Institución ITBT (código ITBT-2026, R.M. 1049/2023, sede El Alto).
2. Usuario admin / admin2026 (bcrypt 10, mustChangePassword=true) + persona +
   empleado EMP-00001 DIRECTIVO "Rector".
3. Permisos (ensurePermissions) y roles (seedRoles); asigna ADMIN.
4. Carreras: Autotrónica (AUT) y Mecánica Automotriz (MEC), 3 años / 6 niveles,
   plan de estudios jsonb (3600 h, 30 h/semana, 120 h/mes, 600 h/semestre);
   ~39 materias por carrera con códigos (SOM-100, MAA-100...) y prerequisitos;
   totalHours = weeklyHours × 20 semanas.
5. Gestiones por carrera (PERIODS_TEMPLATE):
   - I/2025 (CLOSED) 2025-02-03 → 2025-07-04
   - II/2025 (CLOSED) 2025-08-04 → 2025-12-19

OBSERVACIONES TÉCNICAS / PENDIENTES
--------------------------------------------------------------------------------
1. GET "de lectura" sin @RequirePermission quedan accesibles a ANY usuario
   autenticado (by-design implícito; convendría acotar por rol).
2. dashboard/teacher es placeholder parcial (mySubjects: 0, estudiantes globales
   en vez de propios).
3. subject-assignments/auto-assign busca materia+gestión SIN paralelo → con
   varios paralelos solo asigna al primero encontrado.
4. TypeORM synchronize: true en dev → esquema derivado de entidades; no hay
   migraciones reales en backend/database/migrations (scripts migration:* no
   encontrarían nada).
5. JWT_SECRET tiene fallback hardcodeado en código (jwt.strategy.ts y config)
   además del ejemplo de dev.
6. Conclusión de estudios no maneja el estado TITLED (solo GRADUATE).
7. No hay endpoints de refresh-token ni cambio de contraseña propio
   (existen DTOs sin usar); reset es vía PATCH /users/:id/reset-password.
8. Frontend no tiene guardas de ruta por permiso por página: la protección real
   está en la API (interceptor 401) y en el menú por permisos.
9. Token JWT en localStorage (XSS) y CORS origin:true con credentials — riesgo
   asumido en desarrollo, revisar para producción.
10. Códigos de estudiante en el seed empiezan por EST-2026 para todos los
    ingresos (no por año de ingreso).
